# Demo 4.5 — `omp commit`, `omp git`, `conflict://` (≤ 60 s)

## Part A — `omp commit` (real output, omp 18.3.x; the first two runs without a provider logged in)

```text
$ omp commit --help
Generate a commit message and update changelogs

USAGE
  $ omp commit [FLAGS]

FLAGS
      --push             Push after committing
      --dry-run          Preview without committing
      --no-changelog     Skip changelog updates
      --legacy           Use legacy deterministic pipeline
  -c, --context=<value>  Additional context for the model
  -m, --model=<value>    Override model selection

$ omp commit --dry-run
● Resolving model...
error: No model available for commit generation        ← needs a logged-in provider (Module 1)

$ omp commit --dry-run --legacy
Staging all changes…
Reading staged changes…
error: No model available for commit generation
```

With a provider logged in, `--dry-run` prints the proposed message and stops; without `--dry-run` it commits (and updates changelogs unless `--no-changelog`). The model is resolved from the `commit` role, then `smol` (observed in the failure trace). Real output with a provider, one file staged and another only modified:

```text
$ git status --short
M  README.md
 M docs/spec.md
$ omp commit --no-changelog -c "README only"
● Resolving model...
● Detecting changelog targets...
  └─ (none found)
● Starting commit agent...
...
● Creating commit...
Commit created.
$ git show --stat --format=%s HEAD
docs(readme): added note-a section
 README.md | 2 ++
$ git status --short
 M docs/spec.md                            ← only the staged file was committed
```

With nothing staged, the same command stages and commits every working-tree change. During an in-progress merge it creates a **single-parent** commit and leaves `MERGE_HEAD` (observed: `git status` → "All conflicts fixed but you are still merging") — conclude merges with `git commit`.

```text
$ omp git --help
Interactive fullscreen git UI: split diff viewer, staging sidebar, and commit composer
USAGE
  $ omp git [REVISION] [FLAGS]
  -C, --dir=<value>  Run in another directory instead of the current one
```

## Part B — conflict markers → `conflict://` (real `omp read` output on the lab's `conflict-lab` merge)

```text
$ git switch -c scratch main && git merge conflict-lab
Auto-merging api/server.py
CONFLICT (content): Merge conflict in api/server.py
Auto-merging cli/__main__.py
CONFLICT (content): Merge conflict in cli/__main__.py
Automatic merge failed; fix conflicts and then commit the result.

$ omp read api/server.py:conflicts
⚠ 1 unresolved conflict in api/server.py
- ours = HEAD
- theirs = conflict-lab
NOTICE: Bulk-resolve with `write({ path: "conflict://*", content })`, or address a single block with
`write({ path: "conflict://<N>", content })`. Inspect a block by reading `conflict://<N>` (add `/ours`
/ `/theirs` / `/base` for a single side).
`content` shorthand: `@ours` / `@theirs` / `@base` / `@both` lines expand to the recorded sections;
`@both` = ours-then-theirs (additive conflicts only — never for competing edits of the same lines).
Per-id bulk: content of `<id>: @side` lines (e.g. "1: @ours\n2: @theirs") resolves each listed id in
one call. Non-token lines pass through verbatim. Writes replace ONLY the marker block — never repeat
the surrounding lines. Keep one side or combine faithfully; never invent content beyond the recorded sides.

#1  L18-22

$ omp read conflict://1
Conflict #1 not found. Conflict ids are registered when `read` surfaces a marker block; re-read the
file to get a current id.                              ← ids are session-scoped: use them inside the session
```

Inside a session (real tool results from an `omp -p --no-session` run on the same merge; card rendering illustrative):

```text

▸ read  api/server.py:conflicts        ⚠ 1 unresolved conflict … #1 L18-22   (ids continue across files in one session)
▸ read  cli/__main__.py:conflicts      ⚠ 1 unresolved conflict … #2 L17-21
▸ read  conflict://1/ours
▸ read  conflict://1/theirs
▸ write conflict://*
        1: @ours
        2: @theirs
  Resolved 2 conflicts across 2 files:
    api/server.py: 1 conflict
    cli/__main__.py: 1 conflict
  Snapshots:
    [api/server.py#E993]
    [cli/__main__.py#0EC5]
▸ read  api/server.py:conflicts        No unresolved git merge conflicts in api/server.py.
▸ bash  python3 -m unittest discover -s tests   … OK
```

Afterwards `git diff --name-only --diff-filter=U` still lists both files until you `git add` them; conclude with `git commit`.
