# Demo 9.3 — learn a lesson, promote it to a managed skill, read it next session (~60 s)

> Illustrative transcript (no recording on the build machine). Tool result strings come from `omp://tools/learn.md` and `omp://tools/manage_skill.md`; the issue #6 facts (error text, cause, files) are from `omp-course-lab/docs/ISSUES.md` and `api/db.py`. `memory.backend: mnemopi`, `autolearn.enabled: true`, cwd `omp-course-lab/`.

```text
$ omp config get autolearn.enabled
true
$ omp
```

```text
> read docs/ISSUES.md, reproduce issue #6, and find the real cause. Don't fix yet.

  ▸ read  docs/ISSUES.md
  ▸ bash  DATABASE_URL=sqlite:///data/lab.sqlite python3 -m cli users 1
          error: database is locked (is another process using data/lab.sqlite?)
  ▸ grep  "database is locked"
  ▸ read  api/db.py
  ▸ bash  python3 -c "import sqlite3; sqlite3.connect('sqlite:///data/lab.sqlite').execute('select 1 from users')"
          sqlite3.OperationalError: unable to open database file

  The error message blames a lock, but nothing is locked. db_path() returns
  DATABASE_URL unchanged, so sqlite3.connect() gets "sqlite:///data/lab.sqlite",
  treats "sqlite:" as a directory and fails with "unable to open database
  file"; connect() then swallows that OperationalError and raises the invented
  "database is locked" LabError. Fix: strip the sqlite:/// prefix in db_path()
  and report the real cause (with the path) in connect().

> learn this as one durable lesson: the misleading error, the real cause,
  and the check to run first. No skill yet.

  ▸ learn  memory: "In omp-course-lab, 'database is locked' from python3 -m cli
                    is invented by api/db.py connect(); the real cause is
                    DATABASE_URL passed to sqlite3.connect unchanged (sqlite:///
                    prefix or missing file). Check the DATABASE_URL value before
                    hunting for locks."
           context: "issue #6, docs/ISSUES.md"
    Lesson stored.

> now turn the diagnosis into a managed skill named lab-issue-6-misleading-error
  with a one-line description and a numbered procedure.

  ▸ manage_skill  action: create
                  name: lab-issue-6-misleading-error
                  description: "Diagnose the misleading 'database is locked' error in omp-course-lab"
                  body: "## When python3 -m cli says 'database is locked'\n1. Do not look for locks, WAL files or a running server.\n2. Print DATABASE_URL; a sqlite:/// prefix or a missing file is the cause.\n3. Fix api/db.py db_path()/connect(); run LAB_ISSUE=6 python3 -m unittest tests.test_issues."
    Created managed skill "lab-issue-6-misleading-error" (managed-skills/lab-issue-6-misleading-error/SKILL.md).

  Done — the skill is active in this session already (manage_skill refreshes
  the skill list), and it will be discovered in every future session.
```

```text
$ cat ~/.omp/agent/managed-skills/lab-issue-6-misleading-error/SKILL.md
---
name: lab-issue-6-misleading-error
description: Diagnose the misleading 'database is locked' error in omp-course-lab
---
## When python3 -m cli says 'database is locked'
1. Do not look for locks, WAL files or a running server.
2. Print DATABASE_URL; a sqlite:/// prefix or a missing file is the cause.
3. Fix api/db.py db_path()/connect(); run LAB_ISSUE=6 python3 -m unittest tests.test_issues.
```

```text

```

What to notice:
- `learn` stored the lesson **first**; had a skill been requested in the same call and failed validation, the lesson would still be on disk.
- `manage_skill` refreshed the running session; a skill created via `learn` would only appear after `/new`.
- The frontmatter was generated — the body you supplied had none.
- Discovery of `managed-skills/` is unconditional; even with autolearn switched off later, `skill://lab-issue-6-misleading-error` keeps resolving. An authored skill with the same name would shadow it.
