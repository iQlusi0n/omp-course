# Instructor notes — G2 (checkpoint / rewind on issue #7)

## What a passing run looks like
1. First tool card is `checkpoint` with result `Checkpoint created.` / `Goal: …` / `Run your investigation, then call rewind with a concise report.` No id in the result — that is expected.
2. The investigation: many `read`/`grep`/`bash` cards. Fixture #7 is designed so the obvious suspect is innocent; a good run reads the suspect, rules it out with a targeted test, then finds the real cause elsewhere.
3. `rewind` card: `Rewind requested.` / `Report captured for context replacement.`
4. The turn ends. The rewind is applied at `turn_end`: the session branches at the checkpoint entry with a `branch_summary` (the report), and a hidden `rewind-report` custom message is appended. `context_pct` on the status line falls.
5. Follow-up "What was the red herring?" is answered from the report. If the model calls `rewind` again it gets `Checkpoint already completed; continue from the retained rewind report instead of calling rewind again.` — that is a tool error, not a learner failure, but it means the prompt was confusing; move on.

## Measuring "context % drops"
- Use the default status line: `context_pct` is in `statusLine.rightSegments` by default (`["session_name","token_total","cost","context_pct"]`). If a learner changed `statusLine.preset` to `minimal`, have them set it back or add `context_pct` to a custom segment list.
- Compare the peak during the investigation against the value after the prompt returns. Mid-turn the number has not dropped yet — the tool card is only a *request*.
- A tiny investigation (2–3 cards) may drop by a percentage point or less; ask for "thorough" and "run the tests" to make the effect visible.

## Things that are *not* affected (learners often expect otherwise)
- Files edited during the investigation stay edited (`git status` proves it). Rewind is a session-tree operation only.
- Artifacts (`artifact://…`) created during the investigation remain readable.
- The abandoned branch is still in the session `.jsonl`; `/tree` shows it. Tree navigation rebuilds checkpoint/rewind state from whichever branch becomes active (`omp://tree.md`, `omp://tools/checkpoint.md`), so moving the leaf around here muddies the exercise — keep the tree read-only (`Esc`) for this exercise.

## Guided variant (trigger the guard)
Prompt: "Set a checkpoint with goal '…', investigate #7, then stop and just tell me in chat — do not call rewind." The session's settle guard injects a developer-role `<system-warning>` ("You are in an active checkpoint. You MUST call rewind …") and schedules another turn; the model then calls `rewind`. The observable is that the turn never ends without a `rewind` card. The warning itself is a message to the model and may not be rendered.

## Stretch (nesting)
A second `checkpoint` while one is active → `ToolError("Checkpoint already active.")`. The original checkpoint remains active; a later `rewind` branches at the *first* checkpoint's entry.

## Subagent note (forward reference to M10/M11)
Subagents do not get these tools by default. A custom agent's frontmatter `tools:` list must name `checkpoint` or `rewind`; naming either auto-includes the other.
