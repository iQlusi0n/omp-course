# Instructor notes — S1 (memory_edit) and S2 (local backend)

## S1 — correct a fact with `memory_edit`

Reference sequence (Mnemopi):

1. `recall` for "tests database DATABASE_URL" → bullet with `(id: <id>)`. If the preview ends in `…` it was clipped at 500 chars — one more reason for step 2.
2. `read memory://<id>` → full row, frontmatter shows `store: working`, `memory_type: fact`. **This card must precede the update.** The model-facing prompts require it; if a learner's model skipped it, the exercise fails on its own terms even though the tool would have accepted the call — explain why (wholesale replace would silently drop any unseen tail).
3. `memory_edit { op: "update", id, content: "<full corrected text>" }` → `Memory <id> updated in bank <bank> (working).` The corrected text keeps the original sentence and adds that the `sqlite:///` form from `.env.example` only works once issue #6 is fixed in `api/db.py` (before that, only a plain path works).
4. `/new` → `recall` for "DATABASE_URL sqlite:/// form" → the bullet now contains `sqlite:///`.
5. `/memory stats` → Mnemopi bank statistics.

Status semantics to check the learner understands:
- `not_editable` → the id is a fact-table row (read-only). Fix: `retain` a new fact.
- `not_found` for an id that `recall` clearly returned → the row is *episodic* (auto-retained turn). `update`/`forget` support working memory only; use `invalidate`.
- `importance` outside 0..1 is clamped, not rejected.
- `update` with neither `content` nor `importance` throws `memory_edit update requires content or importance.`

### Bonus — `invalidate` + `replacement_id`
Sequence: `retain` the corrected fact (get its id from the `retain`→`recall` round trip), then `memory_edit { op: "invalidate", id: <old>, replacement_id: <new> }` → `Memory <old> invalidated in bank <bank> (<store>)`.
Model answer for "when would you prefer it": *when the old memory's history may still matter — invalidate soft-supersedes and records the replacement, whereas `forget` hard-deletes and `update` erases the old text.* Also: `invalidate` is the only op that works on episodic rows.

## S2 — `local` backend and `learned.md`

Expected observations after switching `memory.backend: local` (with `autolearn.enabled: true`) and restarting:

- Ask "can you call retain/recall/reflect/memory_edit?" → no. `omp://memory.md`: those tools are not available for the local backend. `learn` and `manage_skill` are.
- `learn { memory: "…" }` → `Lesson stored.` (approval tier `write` on this backend — a prompt in `always-ask`). The file is `~/.omp/agent/memories/<encoded-cwd>/learned.md`; the lesson is the newest bullet; a second identical lesson is deduplicated; lessons are secret-redacted before being written (the docs do not list the patterns — the course's fake `labtok_…` token from `.env.example` may or may not match, so do not grade on it).
- Same session: `read memory://root/learned.md` already resolves (it is a file), but the lesson is only *injected* (Memory Guidance) from the next session — the doc says a `learn` call does not mutate the active session's prompt-cache prefix.
- `read memory://root` (= `memory_summary.md`) will typically fail or be empty today: consolidation only processes sessions idle ≥ 12 h, at the next startup. Have learners run `/memory enqueue` and check `memory://root/MEMORY.md` tomorrow if they want to see phase-2 output; not gradable in class.

Restore `memory.backend: mnemopi` afterwards, or remove the block; the `mnemopi/` databases are untouched by the switch.
