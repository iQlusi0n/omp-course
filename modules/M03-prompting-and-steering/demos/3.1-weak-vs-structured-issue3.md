# Demo 3.1 — Weak vs structured prompt on issue #3 (side by side)

Representative transcripts, not recordings (no recorder on the build machine). Card glyphs are schematic: `›` your message, `●` a tool card, `✗` an error-marked card, `⋯` elided lines. Your run will differ in wording and counts; compare the **shape**: did a verifying `bash` card exist, and did it run before the model said "done"?

Fixture: `docs/ISSUES.md` #3 — *CLI: `orders` has no `--format csv`*. Files: `cli/__main__.py`, `cli/commands.py`. Gated test: `LAB_ISSUE=3 python3 -m unittest tests.test_issues`.

## Left: weak prompt

```text
› add csv output to the orders command

● glob cli/**/*.py
● read cli/__main__.py
● read cli/commands.py
● edit cli/__main__.py            +1 −1   (adds "csv" to --format choices)
● edit cli/commands.py            +9 −1   (new render_csv, print(",".join(...)))

I added a `--format csv` option to the `orders` command. The CSV writer joins
each order's fields with commas. You can run it with
`python -m cli orders --format csv`.
```

Read it critically (Lesson 3.5):
- 5 tool cards, **0 `bash` cards** — nothing was executed.
- Header order is whatever the model chose; the issue's expected header (`id,user_id,created_at,status,total_cents`) was never read.
- "You can run it with …" — a claim, not a run. Your `!LAB_ISSUE=3 python3 -m unittest tests.test_issues` afterwards is the first test this code ever saw.

## Right: structured prompt (Lesson 3.1 **Concepts**)

```text
› Implement issue #3 from @docs/ISSUES.md: add `--format csv` to the `orders` CLI command.
  Outcome: … Acceptance: … Verification: … Finish with: files changed and commands run.
  [docs/ISSUES.md inlined by the @ mention]

● read cli/__main__.py
● read cli/commands.py
● read tests/test_issues.py
✗ bash LAB_ISSUE=3 python3 -m unittest tests.test_issues
    ⋯
    FAILED (errors=1)
    Command exited with code 1
● edit cli/__main__.py            +1 −1
● edit cli/commands.py            +14 −1  (csv module, header row, one row per order)
● bash LAB_ISSUE=3 python3 -m unittest tests.test_issues
    ⋯
    OK
● bash python3 -m unittest discover -s tests
    ⋯
    OK
● bash python3 -m cli orders --month 2026-03 --format csv | head -3
    id,user_id,created_at,status,total_cents
    ⋯

Files changed:
- cli/__main__.py — add `csv` to the `--format` choices
- cli/commands.py — `render_csv()` using the csv module; header id,user_id,created_at,status,total_cents

Commands run:
1. LAB_ISSUE=3 python3 -m unittest tests.test_issues   (before: exit 1; after: OK)
2. python3 -m unittest discover -s tests               (OK)
3. python3 -m cli orders --month 2026-03 --format csv | head -3
```

Read it critically:
- 9 tool cards, **4 `bash` cards**; the first is error-marked on purpose (step 1 of Verification: confirm the test fails before changing anything).
- The repro command's first line is the exact header from the issue — in a card, not in prose.
- The receipt lists commands you can re-run yourself with `!`.

## What to record in `notes/m3.md`

| | Weak | Structured |
|---|---|---|
| Tool cards | 5 | 9 |
| `bash` cards | 0 | 4 |
| Tests ran before "done"? | no | yes (fail → pass) |
| Files changed listed? | vague | per file |
| `!git diff --stat` matches summary? | n/a | yes |

The point is not that the structured run is longer. It is that every claim in its final message has a card above it.
